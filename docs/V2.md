# Amazing Law Overlay 2

Приложение разделено на независимые части:

| Часть | Запуск из исходников | Назначение |
| --- | --- | --- |
| Бэкенд | `scripts/run/run_backend.bat` | SQLite, поиск, парсер, ИИ, локальный API |
| Управление | `scripts/run/run_manager.bat` | Источники, обновление, API, оформление, диагностика |
| Внешний клиент | `scripts/run/run_overlay.bat` | Компактный ридер, поиск, чат поверх игры |
| Внутриигровой клиент | `AmazingLawClient.dll` **или** `.asi` | C++/ImGui, D3D9, DirectInput, тот же API |

Окно управления и внешний клиент сами запускают бэкенд при необходимости.
Бэкенд продолжает работать после закрытия окна управления. Один экземпляр
каждого приложения защищён `QLockFile`.

## Начало работы

1. Запустить `scripts/run/run_manager.bat`. Нужен Python 3.10+; зависимости устанавливаются в `.venv`.
2. На первом запуске импортируются существующие `laws/*.txt` и ссылки `urls.txt`.
   Неоднозначные файлы остаются на диске. Источник и ID темы используются для объединения дублей.
3. Добавить источник через предпросмотр или импортировать список ссылок.
4. Во вкладке «Обновление» обновить выбранные или все включённые темы.
   Старые TXT помечены «без исходной структуры»: таблицы появятся после повторного скачивания.
5. Настроить ИИ и нажать «Проверить сохранённое соединение».
6. Запустить внешний клиент или один DLL/ASI-клиент.

Папка `laws/` автоматически не перезаписывается. Совместимый экспорт TXT/JSON
и `index.csv` доступен отдельной кнопкой или через CLI.

Если сайт требует проверку браузером, включить соответствующий флажок и повторить
предпросмотр/обновление. Открытие браузера — явное действие пользователя.
Парсер работает последовательно с паузой между страницами. Для отмены не нужно ждать
всей очереди; текущая загрузка может завершаться до сетевого таймаута.

Chromium устанавливается в пользовательский кэш `%LOCALAPPDATA%\ms-playwright`.
Установщик и парсер в EXE используют один и тот же каталог; отдельная установка
в `_internal` не нужна. Явный `PLAYWRIGHT_BROWSERS_PATH` в окружении имеет приоритет.
Во вкладке «Диагностика» есть проверка запуска Chromium без обращения к форуму.

CLI использует тот же сервис:

```powershell
.\.venv\Scripts\python.exe -m amazing_overlay.cli --urls urls.txt --export laws
.\.venv\Scripts\python.exe -m amazing_overlay.cli --visible
```

Старые `law_overlay.py` и `playwright_laws_parser.py` при прямом запуске направляют
в новые точки входа. Старые классы временно сохранены для проверки регрессий.

## Внешний оверлей

Использовать с игрой в **оконном режиме без рамки**. Обычное внешнее окно
не гарантирует работу поверх эксклюзивного полноэкранного режима. При вводе
оно получает фокус, поэтому временный АФК возможен — это согласованный запасной вариант.

| Действие | По умолчанию |
| --- | --- |
| Показать в просмотре / скрыть | Ctrl+L |
| Переключить ввод и фокус поиска | Alt+F |
| Ввод → просмотр → скрыть | Esc |
| Прокрутка | Alt+↑ / Alt+↓ |
| Предыдущий / следующий закон | Alt+← / Alt+→ |

Хоткеи регистрируются только при активной игре `amazing.exe` или окне оверлея.
Удержание клавиши не вызывает повторных переключений. Ошибка регистрации
отображается в трее; старый оверлей нужно закрыть, если он занимает те же сочетания.
После изменения сочетаний перезапустить клиент.

В просмотре клики проходят в игру, окно не активируется. При выходе из ввода
фокус возвращается сохранённому окну игры, только если оверлей всё ещё активен.
При Alt+Tab приложение не перетягивает фокус обратно.

Список и чат раскрываются отдельно. Доступны оглавление, избранное, недавние документы,
поиск по всей базе и переход по источникам ИИ. Геометрия, документ, прокрутка
и панели сохраняются в бэкенде. Перетаскивать окно можно за заголовок в режиме ввода.

## DLL / ASI

У установленного клиента проверены PE x86 и импорт `Direct3DCreate9`/`DirectInput8Create`.
Собирается **32-битная** DLL. `.asi` — копия той же DLL; одновременно использовать
оба файла нельзя. В проекте нет инжектора и автоматического изменения файлов игры.
При Manual Map загрузчик должен выполнять инициализацию C++ runtime и сохранять
отображение модуля до завершения игры; ручная выгрузка при установленных перехватах не поддерживается.
Используйте свой совместимый способ загрузки, предварительно проверив правила сервера.
Официальное разрешение проекта на этот плагин не установлено.

DLL отрисовывает документы/таблицы, выполняет поиск и запросы ИИ через named pipe.
Сеть, SQLite и Chromium остаются вне игры. Работа IPC выполняется отдельным потоком,
не в `EndScene`. Интерактивный режим подавляет сообщения окна и DirectInput;
попытки игры центрировать и ограничивать курсор через `SetCursorPos`/`ClipCursor`
подавляются только во вводе при активном окне игры. При Alt+Tab ограничения освобождаются.
самостоятельная симуляция активности и изменение серверного АФК не выполняются.

**Статус: экспериментальный клиент.** Сборка и изолированный D3D9 smoke-тест
не доказывают совместимость с конкретными графическими модами, загрузчиком и камерой Amazing.
Перед обычным использованием нужна ручная приёмка по `docs/GAME_ACCEPTANCE.md`.
До её прохождения внешняя версия остаётся основной. DLL закрепляется в процессе;
безопасная динамическая выгрузка не поддерживается, для удаления перезапустите игру.

Если панель не появилась, проверять `%LOCALAPPDATA%\AmazingLawOverlay\v2\native-client-<PID>.log`.
Журнал показывает вход в DLL, установку перехватов, первый `EndScene`, режим ввода
и точные коды ошибок. Отсутствие журнала означает, что запуск DLL подтвердить нельзя.

Обычная сборка (VS 2022 с C++ и Windows SDK, CMake 3.24+):

```powershell
.\scripts/build/build_native.bat
```

Если MSVC установлен без Windows SDK, есть локальный вариант, не меняющий систему:

```powershell
powershell -File scripts/acquire_sdk.ps1
powershell -File scripts/build_local_sdk.ps1
```

Он скачивает официальные NuGet SDK-пакеты в игнорируемую `.cache/` и использует Ninja.
Обычная сборка лежит в `native/out/Release/`, локальная — в `native/out-local/`.
`overlay_native_smoke.exe` — отдельное тестовое приложение, **не** загрузчик в игру.

## Данные и ИИ

Рабочая папка: `%LOCALAPPDATA%\AmazingLawOverlay\v2`.
Здесь находятся `laws.db`, история версий, `settings.json`, `.env`,
`browser-profile/`, блокировки экземпляров и `diagnostics.log`.
У каждого участника группы собственные ключи, cookies и база.

Настройки: defaults → старый `config.json` → пользовательский `settings.json` → `.env` → окружение.
Пользовательская `.env` имеет приоритет над `.env` рядом с исходниками.
Переменные процесса `AI_*` имеют высший приоритет; UI показывает активные переопределения.
Ключ из UI сохраняется только в пользовательскую `.env`, в JSON и ответы `settings` не попадает.
Пустое поле ключа означает «оставить прежний».

База хранит JSON-документы schema v1 и FTS5-индекс секций. Публикация документа,
версии и индекса атомарна. Повторное скачивание неизменённого содержимого не создаёт
новую версию. Внешние картинки остаются ссылками: чтение не требует сетевой загрузки.

ИИ получает релевантные секции из всей выбранной базы, соседние положения,
семантический текст таблиц и ограниченную историю диалога. При слабом совпадении
выполняется дополнительный запрос на расширение поиска. Он также расходует токены.
Свободные модели могут иметь собственные ограничения доступности и частоты запросов.

В первой версии используется лексический поиск с расширением запроса, без embeddings.
Бюджет контекста задаётся символами; он не является точным счётчиком токенов модели.
UI показывает использование, когда API его возвращает; стоимость не вычисляется
по неподтверждённому прайсу. Источники `[S1]` открывают реальные документы,
неизвестные маркеры не становятся ссылками. Правильность вывода всё равно нужно проверять по тексту.

## Переносимая сборка

```powershell
.\scripts/build/build_portable.bat
```

Результат — **вся папка `Release/` в корне проекта**, включая `_internal`,
DLL/ASI и лицензии. Эта папка коммитится в Git и готова для передачи пользователям.
Сборка сначала обновляет нативный клиент, собирает приложение в
`.cache/dist/portable-build/AmazingLawOverlay`, проверяет его и копирует комплект в `Release/`.
Файл `Release/manifest.json` хранит размеры и SHA256; проверка:
`.venv\Scripts\python.exe scripts/publish_release.py --check`.
Python пользователям не нужен. При первом запуске открыть `start_manager.bat`,
во вкладке «Обновление» установить Chromium. Для группы экспортировать список ссылок
и передать отдельно; сборка намеренно не включает местные законы, ключи и cookies.

DLL/ASI обязательны для полной сборки. Бэкенд/менеджер — x64, игровой модуль — x86;
они общаются через IPC и не обязаны иметь одинаковую разрядность.

После `scripts/build/build_native.bat` актуальная DLL доступна по единому пути
`.cache/dist/native-latest/AmazingLawClient.dll`. Сборка также обновляет существующие копии
DLL/ASI в `.cache/dist/` и проверяет их SHA256, чтобы сохранённый путь инжектора не указывал
на старую версию. Замена файла не обновляет модуль в уже запущенной игре — нужен полный перезапуск игры.

## Поиск в игровом клиенте

Слева законы показаны отдельными карточками с переносом названий и подсветкой выбора.
Поиск фильтрует библиотеку и подсвечивает совпадения в открытом законе, включая таблицы.
Счётчик рядом с поиском относится к открытому документу. Кнопки `<` / `>` переходят
между совпадениями по кругу; F3 / Shift+F3 делают то же, Enter / Shift+Enter работают
при вводе в строке поиска. Текущее совпадение выделено ярче и прокручивается в область чтения.
Alt+Left / Alt+Right по-прежнему переключают документы. «Сброс» очищает запрос.

## Настройки внутри ASI / DLL (2.1)

В режиме ввода (Alt+F) нажмите шестерёнку в шапке. Здесь доступны прозрачность всего окна
30–100%, общий размер шрифта 14–26 px, переключатель светлой темы и включение анимации
появления/скрытия за 0,2 с. Оформление применяется для предпросмотра; «Отмена» возвращает
сохранённый вид. «Сохранить» сохраняет оформление и настройки API через бэкенд.
Шрифты заранее загружаются для каждого размера: движение ползунка не пересоздаёт устройство.
После скрытия ввод освобождается независимо от завершающейся анимации.

В разделе ИИ можно задать провайдера, API-адрес, модель, ключ и лимит ответа.
Пустое поле ключа сохраняет прежний ключ. Проверка соединения использует введённые поля
без сохранения и показывает фактические провайдер/модель; её можно остановить.
Ключ хранится в пользовательском `.env`, не попадает в публичный RPC настроек и `settings.json`.
Переопределения из `.env` и окружения показаны в панели. Проверка и сохранение имеют одинаковый
приоритет окружения; переменная процесса `AI_API_KEY` имеет приоритет над введённым ключом.

Для этих функций нужны **и новая DLL/ASI, и бэкенд 2.1**. Переносимый комплект текущего обновления:
`Release/`. Закройте прежний бэкенд и запустите `start_backend.bat`
из нового комплекта (либо запустите его `start_manager.bat`). Не запускайте параллельно старый
бэкенд: единственный экземпляр продолжит обслуживать подключения. Данные и ключ остаются
в `%LOCALAPPDATA%/AmazingLawOverlay/v2`, повторно импортировать базу не нужно.
DLL/ASI обновляется только после полного перезапуска игры; актуальная копия — в `.cache/dist/native-latest`.

## Проверки

```powershell
$env:AMAZING_OVERLAY_PIPE='amazing-law-overlay-v2-tests'
$env:QT_QPA_PLATFORM='offscreen'
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m py_compile law_overlay.py
.\.venv\Scripts\python.exe test_overlay_linux.py --smoke
.\.venv\Scripts\python.exe scripts/check_live_parser.py
```

Последняя проверка обращается к форуму и сохраняет результат только в `.cache/`.
Остальные используют временную базу; нативный smoke запускается при наличии собранного
`native/out-local/overlay_native_smoke.exe`. Он не внедряет код в игру.
Для Linux проверки старых Win32-хоткеев не выполняются.

Подробности протокола: `docs/PROTOCOL.md`. Приёмка игры: `docs/GAME_ACCEPTANCE.md`.
